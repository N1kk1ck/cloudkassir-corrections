# CloudKassir Corrections

Локальный инструмент для подготовки, проверки и контролируемой отправки
чеков коррекции через CloudKassir. Организации и формат входных таблиц
настраиваются без изменения кода.

На вход нужны три источника:

1. YAML со списком организаций, API-доступами и фискальными настройками.
2. CSV/XLSX со списком чеков, которые нужно сформировать.
3. CSV/XLSX с товарными позициями этих чеков.

Результат проверки — готовые чеки, отдельный список проблем и JSONL-предпросмотр
запросов. Подготовка работает без интернета и не обращается к CloudKassir.

## Возможности

- Любое количество организаций с произвольными стабильными entity_id.
- Чтение обычных CSV/XLSX без скрытого pivot-cache и без привязки к конкретной CRM.
- Соответствие колонок, выбор листа и строки заголовков, перевод значений.
- Раздельное сопоставление заказов разных организаций.
- Проверка дублей и точное сравнение денежных сумм через Decimal.
- Отдельное подтверждение состава возврата.
- Локальный веб-интерфейс подготовки без кнопки реальной отправки.
- Явная отправка через CLI, журнал SQLite и детерминированные X-Request-ID.
- Неопределённые запросы не повторяются автоматически. Завершённым считается
  только чек со статусом processed.

## Быстрый старт

Нужен Python 3.11 или новее.

Windows:

~~~powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
~~~

Linux/macOS:

~~~sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python app.py
~~~

Откройте http://127.0.0.1:8765. На Windows также можно запустить START.bat.
Интерфейс слушает только локальный адрес; это приложение для своего компьютера.

Для первого знакомства загрузите config/organizations.example.yaml,
examples/receipts.csv и examples/items.csv. Это вымышленные данные. Пример
содержит два готовых чека и один чек с намеренным расхождением суммы.
Демонстрационная конфигурация заблокирована для реальной отправки.

## Проверка из командной строки

Далее python означает Python из установленного виртуального окружения.
Команды выполняются из папки проекта.

~~~sh
python -m receipt_tool prepare --config config/organizations.example.yaml --receipts examples/receipts.csv --items examples/items.csv --output output/demo
~~~

В output/demo появятся:

- ready.csv — идентификаторы готовых чеков;
- review.csv — чеки, требующие проверки, и причины;
- payload_preview.jsonl — будущие запросы, без API-доступов;
- summary.json — количество готовых и проблемных чеков.

В демо ожидается код завершения 2: один чек специально требует проверки.
Это не сбой установки. Подготовка не создаёт базу отправки.

## Свои организации и таблицы

Скопируйте config/organizations.example.yaml в config/organizations.yaml.
Добавляйте произвольные ключи в organizations. Для CloudKassir нужна пара
Public ID и API Secret; их можно хранить в локальном YAML или передавать через
переменные окружения, указанные в public_id_env и api_secret_env.
Для offline-подготовки реальные доступы не требуются.

Фискальные значения задаются отдельно для каждой организации. Доступов к API
недостаточно: ИНН, налогообложение, НДС, основание коррекции и остальные
реквизиты должны быть получены и проверены пользователем.

Поместите свои таблицы в input. Их стандартный формат подробно описан в
[docs/input-format.md](docs/input-format.md). Если заголовки или значения
другие, создайте mapping.yaml на основе config/mapping.example.yaml:

~~~sh
python -m receipt_tool prepare --config config/organizations.yaml --receipts input/receipts.xlsx --items input/items.xlsx --mapping config/mapping.yaml --output output/current
~~~

Сопоставление не угадывается по названиям файлов. У чека есть entity_id,
receipt_id и order_id; у каждой позиции — entity_id и order_id. Когда на один
заказ приходится несколько чеков, нужен также receipt_id каждой позиции.

## Область поддержки

Версия 0.1 поддерживает ФФД 1.2, самостоятельную коррекцию прихода и возврата
прихода, RUB, электронную оплату и полный расчёт (method=4) для интернет-платежей.
Скидки и баллы должны уже входить в итоговые суммы позиций. Доставка передаётся
отдельной позицией. Автоматического объяснения недостающей суммы скидкой нет.

Маркировка, агентские и отраслевые реквизиты, смешанные способы оплаты,
авансы/кредиты и коррекция расхода в этой версии не реализованы.
Обычные чеки вместо чеков коррекции также не формируются.
Новые источники можно привести к стандартным таблицам или добавить адаптер.

Форма запросов сверена с [официальной документацией CloudKassir](https://developers.cloudkassir.ru/).
Автоматическая проверка не подтверждает правомерность основания коррекции
или правильность выбранного налогового режима.

## Реальная отправка

Сначала просмотрите отчёты и JSONL. Реальные вызовы API в тестовом наборе
отсутствуют; до рабочей отправки требуется проверка реквизитов и одного чека.

Для новой установки создайте журнал один раз:

~~~sh
python -m receipt_tool init-state --confirm NEW_INSTALLATION
~~~

Если отправки уже были, восстановите актуальный журнал этой установки.
Потерянная база не восстанавливается из Git. Не создавайте новую базу вместо
утраченной. Чужая или несовместимая схема SQLite отклоняется; автоматической
миграции из других программ нет.

После проверки реквизитов задайте demo: false и fiscal_confirmed: true в
настройках выбранной организации. Следующая команда является реальной
фискальной операцией; запускайте её только после явного одобрения ответственного:

~~~sh
python -m receipt_tool send --config config/organizations.yaml --receipts input/receipts.xlsx --items input/items.xlsx --entity your_entity --send --confirm SEND_CORRECTIONS --limit 1
~~~

При использовании нестандартных колонок добавьте тот же --mapping, что и
при подготовке. --limit ограничивает новые отправки; уже учтённые чеки
пропускаются. Для организации без ранее подтверждённого processed первая
партия не может содержать более одного нового чека.

Затем запросите конечный статус:

~~~sh
python -m receipt_tool status --config config/organizations.yaml --entity your_entity --poll
python -m receipt_tool report --entity your_entity
~~~

status обращается к API, report читает только локальный журнал. Команда status
не зависит от наличия исходных таблиц. queued означает очередь, delayed —
истекшее ожидание, error — отклонённый чек, unknown — неопределённый результат.
При unknown или sending после прерывания сначала сверяйтесь с CloudKassir:
программа автоматически не повторит такой запрос. Даже error не повторяется
без отдельной стратегии сверки и исправления. Подробности:
[docs/sending-safety.md](docs/sending-safety.md).

Коды завершения: 0 — операция завершена (для отправки только processed);
2 — ошибка входных данных/настроек или есть review при prepare;
3 — в журнале остаются незавершённые либо ошибочные выбранные чеки.

## Хранение данных

В Git включаются код, документация и проверенные вымышленные примеры.
config/organizations.yaml, input, output, runtime и виртуальное окружение
исключены. Предпросмотр содержит контакты покупателей и фискальные реквизиты,
хотя API-ключей в нём нет. Храните его как рабочие данные.

Веб-загрузки, в том числе YAML с доступами, остаются локально в
runtime/uploads. Удаляйте ненужные загрузки средствами файловой системы после
завершения работы; они не являются резервной копией журнала отправок.
