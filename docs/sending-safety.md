# Журнал и реальная отправка

Операции prepare, report и веб-интерфейс не вызывают CloudKassir.
Только команды send и status работают с API. Тестового запроса перед отправкой
нет: обычная диагностика не должна создавать фискальные операции.

## Перед первой отправкой

1. Проверьте законность основания коррекции и фискальные параметры организации.
2. Проверьте идентификаторы операций, контакты, состав и итоги в preview.
3. Для новой установки отдельно создайте журнал через init-state.
4. Для продолжающей работу установки восстановите её прежний журнал.
5. Сначала явно разрешите один чек для одной организации.
6. Запросите статус до processed. Только затем увеличивайте --limit.

## Защита от повторов

X-Request-ID детерминирован по entity_id, receipt_id и receipt_type.
В SQLite сохраняются уникальный идентификатор операции, хеш payload и хеш
Public ID. До HTTP-запроса фиксируется sending в транзакции BEGIN IMMEDIATE.
Второй процесс не может повторно захватить тот же чек.

Любое ранее сохранённое состояние защищено от автоматической повторной
отправки, включая error, unknown и sending после аварийного завершения.
Изменение API-аккаунта уже использованного entity_id также блокируется.
При попытке повторного захвата с изменённым payload требуется отдельная сверка.

Флаг --limit ограничивает новые операции. Ранее учтённые строки пропускаются.
Защита действует в пределах одной сохранённой базы. Создание новой базы,
замена receipt_id или entity_id, независимые копии журнала на двух компьютерах
могут разрушить локальную защиту. Детерминированный request ID не заменяет журнал.

## Неопределённые результаты

Если ответ потерян, запрос мог быть принят. Такой чек получает unknown.
Если процесс прерван после фиксации попытки, остаётся sending.
Автоматического повтора или снятия блокировки по истечении времени нет.
Для unknown без cloud_receipt_id сначала сверьте операцию в CloudKassir
или через поддержку. Не удаляйте запись и не придумывайте новый ID для повтора.

Если cloud_receipt_id получен, status обновляет queued/delayed до конечного
processed или error. По истечении ожидания используется delayed.
Неизвестный ответ API не превращается в processed. API-ошибка или сетевой сбой
останавливают текущую отправку; остальные новые чеки не отправляются.

В первой версии нет автоматического инструмента повторной отправки ошибочных
операций или их ручного перевода в processed. Такая процедура требует отдельного
проектирования со сверкой на стороне сервиса.

## Резервное копирование

Храните runtime/state.db вне Git вместе с защищённой резервной копией.
Остановите процессы отправки перед файловым переносом; если применяется WAL,
используйте согласованный SQLite backup, а не копирование одного файла.
Не объединяйте журналы разных установок простым копированием файлов.

Схема этой версии имеет идентификатор cloudkassir-corrections/1.
Базы других приложений и неподдерживаемые схемы не открываются автоматически.
Перенос действующей установки с другой схемой требует отдельной миграции
и сверки ранее отправленных операций.
